| **RSK-02** | Coordination | Independent AI assistants introducing divergent function signatures, class names, or return types | High | **High** | Frozen shared contract with verbatim code in all 5 prompts; strict file ownership boundaries | Automated contract conformance suite (`tests/test_contract.py`) run before any merge | Member 1 | Reject PR; require AI assistant to align with frozen contract specifications. |
| **RSK-03** | Integration | "Big-bang" late integration resulting in incompatible stages and broken data flow | Medium | **High** | Incremental 8-checkpoint integration sequence (Checkpoint 1 through 8 in `INTEGRATION_AND_TESTING_PLAN.md`) | Automated integration pipeline test suite run after every single component merge | Member 1 | Revert to previous passing checkpoint tag; isolate interface mismatch with unit test doubles. |

## 3. Git Collaboration and Team Workflow Protocol

Because the project workspace is currently uninitialized (`fatal: not a git repository`), the team will establish the following Git workflow to guarantee repository stability and prevent work collisions:

### 3.1 Branching Strategy
```
main (production-ready, submitted releases)
  ▲
  └── integration (continuous integration & checkpoint verification, owned by M1)
        ▲
        ├── feature/m1-shared-infra (M1)
        ├── feature/m2-lexer-printer (M2)
        ├── feature/m3-types-symbols (M3)
        ├── feature/m4-parser (M4)
        └── feature/m5-semantic-analyzer (M5)
```

1. **`main` Branch:** Protected. Contains only verified releases for Phase 1, Phase 2, and Phase 3 submissions.
2. **`integration` Branch:** Main integration staging branch managed by Member 1. All checkpoint tests must pass before anything merges into `integration`.
3. **Feature Branches:** Each member works on an isolated branch named `feature/m<N>-<component>`.
4. **Merge Protocol:**
   - No member merges their own branch into `integration`.
   - Member 1 reviews and merges feature branches after running `python3 -m unittest tests.test_contract` and the full test suite.
   - For Member 1's own feature branches, Member 4 conducts the review and merge.

### 3.2 Formal Interface Change Control Protocol (§15)
If an AI assistant or team member discovers an essential interface defect:
1. The proposer logs a formal Change Request (CR) in `planning/CONTRACT_CHANGES.md`.
2. The CR must state: `CR ID`, date, author, affected files, problem, exact proposed replacement code, and impact analysis.
3. Approval is mandatory from Member 1 and all owners of affected files.
4. Member 1 updates `SHARED_PROJECT_CONTRACT.md`, bumps the contract version, and updates affected member prompts.
5. No member may implement undocumented interface changes independently.
